# Balk — Repository Connection Map

## Implementation Plan

### 1. Purpose

Build a standalone npm package that generates a compact, deterministic **Repository Connection Map** designed specifically for AI-assisted interconnected code changes.

The package is intended for repositories where an implementation change may cross multiple files, modules, directories, languages, or generated data artifacts.

The primary artifact is:

```text
connection-map.md
```

with a canonical machine-readable companion:

```text
connection-map.json
```

The Markdown document is intended to be directly provided to online AI agents such as Claude, Gemini, and ChatGPT.

The JSON document provides the canonical structured representation for tooling and future integrations.

The package is **not intended initially to replace Graphify**. Graphify can continue providing a visual repository relationship map. Visual graph generation can be considered for a later version.

---

# 2. Core Design Principle

The package should answer:

> **If I change this file, function, or data artifact, what other repository components are structurally connected to it and may need to be inspected?**

It should not attempt to answer:

- What are the repository's architectural communities?
- Which modules are "god nodes"?
- Which areas have the highest cohesion?
- What architectural patterns exist?
- What does each file do in natural language?

Those may be useful analyses, but they are outside the primary purpose of this package.

The source files remain authoritative for understanding implementation details.

The Connection Map exists to tell an AI agent **where to look**.

---

# 3. Primary Artifact

The generated output should be:

```text
connection-map.md
connection-map.json
```

The Markdown artifact should remain compact and predictable.

Conceptually:

```text
# Repository Connection Map

Generated: ...

## Repository

...

## File Connections

### src/state/state.js

  → src/sim/sim.js

  → sim.step()

  ← scripts/build.py
```

The exact rendering should be deterministic from `connection-map.json`.

# 4. Graph Model

The underlying model should not be limited to files.

The graph should support several node types.

## 4.1 Code Files

Examples:

```text
src/main.ts
src/state/state.ts
src/components/App.tsx
scripts/build.js
```

## 4.2 Code Symbols

Examples:

```text
src/state/state.ts:updateState
src/state/state.ts:resetState
src/sim/sim.ts:step
```

Symbols should eventually include:

- functions
- methods
- classes
- exported symbols
- relevant constants/types where relationships can be established reliably

## 4.3 Data Files

Data artifacts must be first-class graph nodes.

Examples:

```text
data/source.json
data/normalized.json
data/titles.parquet
data/developers.parquet
```

Supported formats should initially include a broad set of commonly encountered repository data files, including:

```text
JSON
JSONL / NDJSON
CSV
TSV
Parquet
YAML
TOML
XML
SQLite / SQLite-compatible database files
```

Additional formats can be added later.

The goal is not necessarily to parse the contents of every format.

The important first capability is recognizing the artifact and establishing its **producer/consumer relationships**.

---

# 5. Relationship Types

The graph should distinguish relationship types rather than storing everything as a generic dependency.

## 5.1 Code Relationships

Initial relationships:

```text
imports
importedBy
calls
calledBy
extends
implements
references
exports
```

Not every language will support every relationship.

The analyzer should only emit relationships that can be established reliably.

---

# 6. Data Relationships

Data flow is a first-class requirement.

The package must support relationships such as:

```text
generates
generatedBy
consumes
consumedBy
reads
writes
transforms
```

For example:

```text
scripts/collect.py
    generates
        data/games.json

scripts/build.py
    consumes
        data/games.json

scripts/build.py
    generates
        data/games.parquet

src/data/loadTitles.ts
    consumes
        data/games.parquet
```

This allows the Connection Map to represent a pipeline even when no conventional source-code import relationship exists.

---

# 7. Data-Lineage Example

A repository such as the following should be representable:

```text
scripts/
├── collect.py
├── normalize.py
└── build_parquet.py

data/
├── raw.json
├── normalized.json
└── titles.parquet

src/
├── data/
│   └── loadTitles.ts
└── pages/
    └── TitlesPage.tsx
```

The resulting connection map should be able to express:

```text
collect.py
    → generates → raw.json

normalize.py
    → consumes → raw.json
    → generates → normalized.json

build_parquet.py
    → consumes → normalized.json
    → generates → titles.parquet

loadTitles.ts
    → consumes → titles.parquet

TitlesPage.tsx
    → calls → loadTitles()
```

This creates a useful cross-language repository path:

```text
collect.py
  → raw.json
  → normalize.py
  → normalized.json
  → build_parquet.py
  → titles.parquet
  → loadTitles.ts
  → TitlesPage.tsx
```

That path is substantially more useful for interconnected implementation work than a pure import graph.

---

# 8. How Data Relationships Are Discovered

This should use multiple levels of confidence.

## Level 1 — Explicit Code References

Detect data paths referenced directly by source code.

Examples:

```javascript
readFile('data/source.json');
```

```typescript
readParquet('data/titles.parquet');
```

```python
pd.read_json("data/source.json")
```

```python
pd.read_parquet("data/titles.parquet")
```

These should produce high-confidence relationships.

---

## Level 2 — Configuration References

Inspect common configuration and pipeline files for data paths.

Examples:

```text
package.json
pyproject.toml
Makefile
Taskfile
shell scripts
workflow files
pipeline configuration
```

The goal is to recognize relationships such as:

```text
build command
    → produces → data/output.parquet
```

when that relationship is explicitly represented in repository configuration.

---

## Level 3 — Generated Artifact Conventions

Recognize obvious relationships when a repository has clear conventions.

For example:

```text
scripts/build_data.ts
data/build_data.json
```

should not automatically be treated as a dependency merely because the names resemble one another.

Name-based inference should therefore be lower confidence and should not be emitted as a normal relationship unless explicitly enabled.

---

## Level 4 — Explicit Manifest

Provide an optional repository configuration file for relationships that static analysis cannot reliably determine.

For example:

```yaml
data:
  - producer: scripts/collect.py
    output: data/games.json

  - producer: scripts/build_parquet.py
    input: data/games.json
    output: data/games.parquet

  - consumer: src/data/loadGames.ts
    input: data/games.parquet
```

This becomes important for pipelines where paths are constructed dynamically.

The manifest should supplement analysis rather than replace it.

---

# 9. JavaScript / TypeScript Support — Version 1

JavaScript and TypeScript are the primary language targets.

Support:

```text
.js
.jsx
.ts
.tsx
.mjs
.cjs
```

The analyzer should identify, where reliably possible:

- imports
- exports
- re-exports
- functions
- classes
- methods
- function calls
- references to imported symbols
- inheritance
- type references
- dynamic imports where statically detectable

The first implementation should prioritize **reliable relationships over exhaustive relationships**.

A false relationship is more damaging to an AI context map than a relationship that was omitted because it could not be established confidently.

---

# 10. Python Support — Deferred but Prioritized

Python source analysis is explicitly deferred from the first implementation.

However, Python is the first language that should be added after JavaScript/TypeScript because it is a significant part of the intended workflow.

The architecture must therefore avoid making JavaScript/TypeScript assumptions intrinsic to the graph model.

The analyzer interface should support language-specific analyzers:

```text
Analyzer
├── JavaScriptAnalyzer
├── TypeScriptAnalyzer
└── PythonAnalyzer (future)
```

Python support should eventually provide equivalent relationships:

```text
imports
calls
exports
references
generates
consumes
```

Python data-file relationships should **not** wait for full Python AST support.

For example, v1 should still be able to represent:

```text
build.py
    → generates → output.json
```

through explicit configuration or detectable data references even before Python symbol analysis exists.

---

# 11. Data Format Strategy

The package should distinguish between:

### Artifact recognition

Recognizing:

```text
foo.json
foo.parquet
foo.csv
foo.sqlite
```

and:

### Artifact interpretation

Understanding the contents of those files.

Version 1 primarily needs the first.

The package should not attempt to deeply analyze arbitrary data contents merely to produce the connection map.

For example, it does not need to understand every column in:

```text
titles.parquet
```

to establish:

```text
build.py
    → generates → titles.parquet

loadTitles.ts
    → consumes → titles.parquet
```

Schema analysis can be a future feature.

---

# 12. Canonical JSON Schema

`connection-map.json` is the authoritative generated artifact.

A first version should resemble:

```json
{
  "version": 1,
  "repository": {
    "commit": "a81f32c",
    "generatedAt": "2026-09-30T..."
  },
  "files": {},
  "symbols": {},
  "artifacts": {},
  "relationships": []
}
```

Relationships should be explicit objects rather than implicit nested structures.

For example:

```json
{
  "type": "generates",
  "from": "scripts/build.py",
  "to": "data/titles.parquet",
  "confidence": "high"
}
```

and:

```json
{
  "type": "calls",
  "from": "src/state/state.ts:updateState",
  "to": "src/sim/sim.ts:step",
  "confidence": "high"
}
```

This provides flexibility for future relationship types and languages.

---

# 13. Markdown Generation

Markdown should be generated from the canonical graph.

It should not independently perform analysis.

The process is:

```text
source repository
       ↓
language/data analyzers
       ↓
canonical graph
       ↓
connection-map.json
       ↓
Markdown renderer
       ↓
connection-map.md
```

This ensures that the human-readable and machine-readable representations cannot drift apart.

---

# 14. Connection Paths

The Markdown artifact should include useful paths through the graph.

For example:

```text
## Connection Paths

### titles.parquet

build_parquet.py
  → generates → titles.parquet
  → consumed by → loadTitles.ts
  → called by → TitlesPage.tsx
```

However, the renderer should avoid printing every possible graph traversal.

The purpose is to expose useful paths without recreating the entire graph as prose.

Path generation should therefore have sensible limits for:

- traversal depth
- duplicate paths
- cycles
- extremely high-degree nodes

The complete relationship set remains available in JSON.

---

# 15. Git Integration

The package should support automatic regeneration at commit time.

Preferred interface:

```bash
npx balk install
```

This installs a Git hook.

On commit:

```text
git commit
    ↓
connection-map generation
    ↓
connection-map.json
connection-map.md
    ↓
git add generated files
    ↓
commit completes
```

The generated artifacts should contain the current commit identifier when available.

This provides a direct relationship between:

```text
repository state
    ↔
connection-map version
```

# 18. Incremental Generation

The first implementation does not need sophisticated incremental graph computation.

Correctness should come first.

However, the architecture should make incremental generation possible later.

Potential future behavior:

```text
git commit
    ↓
identify changed files
    ↓
reanalyze changed files
    ↓
update affected relationships
    ↓
regenerate artifacts
```

For v1, regenerating the complete graph at commit time is acceptable if performance is reasonable for the intended 10–100 code-file repositories.

---

# 19. Output Location

The default should be:

```text
connection-map.md
connection-map.json
```

or a dedicated directory:

```text
connection-map/
├── connection-map.md
└── connection-map.json
```

The package should allow the output directory to be configured.

It should not require Graphify's `graphify-out/` directory.

Graphify and this package should be able to coexist:

```text
graphify-out/
    graph.json
    GRAPH_REPORT.md
    architecture-graph.html

connection-map/
    connection-map.md
    connection-map.json
```

Graphify remains responsible for visual exploration.

Connection Map remains responsible for AI-oriented interconnected-code context.

# 24. Package Identity

The npm package name is **`balk`**.

The package identity should be consistent across the implementation, CLI, documentation, configuration, and examples:

- npm package: `balk`
- CLI command: `balk`
- configuration file: `.balk.json`
- generated Markdown artifact: `connection-map.md`
- canonical machine-readable artifact: `connection-map.json`
- optional output directory: `connection-map/`

The distinction is intentional:

- **`balk`** identifies the tool/package.
- **`connection-map`** identifies the generated output and artifact format.

All future implementation and documentation references should use `balk` rather than the previous package name.

# 25. Definition of Done

The initial package is successful when a developer can install it into a repository and obtain:

```text
connection-map.md
connection-map.json
```

after a commit, where the Markdown lets an AI agent understand:

1. What files exist.
2. Which files import or depend on other files.
3. Which functions/classes/symbols are connected.
4. Which code calls or is called by relevant symbols.
5. Which data artifacts are generated or consumed.
6. How data moves through a multi-stage pipeline.
7. Which files are likely to be relevant when a particular component changes.

The package does **not** need to understand the entire meaning of the repository.

It needs to provide an accurate map of the repository's **connections**.

That is the product.
